# WideGold V1 总体技术方案

## 1. 项目目标

WideGold V1 是“宽基指数 + 人民币黄金”的市场环境智能研判系统。产品不是让大模型直接预测涨跌，而是将“事实获取、非结构化理解、确定性计算、流程调度、版本治理、展示解释”拆成明确边界。

核心原则：

```text
LLM 负责理解
规则引擎负责计算
Prefect 负责调度
PostgreSQL 负责事实
FastAPI 负责边界
React 负责展示
```

最终输出聚焦：当前环境对不同资产的支持度、Confidence、主要利多/利空、风险和证据链。

## 3. 前端方案

前端位于 `apps/web/`，使用 React + TypeScript + Vite + ECharts。

职责：

- Dashboard：展示最新 Published Snapshot；
- 资产卡片：Score、Label、Confidence、Top Positive/Negative、Risk Flag；
- 历史曲线：Score 与 Confidence；
- Factor Health：27 个逻辑因子、42 个物理状态；
- Admin：登录、System Diagnostics、Runtime Config、Audit、Run Trace；
- 手动分析：创建 Preview，完成后显式 Publish；
- Prefect 不直接暴露给业务页面，业务状态通过 FastAPI 查询。

前端只消费 REST/SSE，不直接访问 PostgreSQL、Redis 或 Prefect 数据库。

## 4. 后端方案

### 4.1 FastAPI

FastAPI 位于 `apps/api/`。它只做：

```text
Auth
参数校验
Query / Command
权限检查
触发 Prefect Deployment
返回 Run ID
```

API 请求本身不执行重型分析、全量抓取、LangGraph 和回测。

### 4.2 Application Service

`src/widegold/services/` 负责组合 Repository、Engine、Provider 与 Runtime Config，作为 API/Workflow 与领域核心之间的应用层。

### 4.3 Deterministic Engine

`src/widegold/engine/` 是项目最重要的可复现核心。包括：

- Indicator feature；
- Factor calculator；
- Factor resolution；
- Conflict / correlation / cap；
- Asset scoring；
- Confidence；
- Quality Gate。

Engine 不应该依赖 FastAPI、Prefect、HTTP 或 SQLAlchemy Session，便于单测、Replay 和离线验证。

## 5. Prefect Workflow

Prefect 是系统级流程编排器。主要生产链：

```text
create/freeze run context
→ collect indicators
→ collect news
→ cluster news
→ event intelligence
→ calculate factor inputs
→ resolve factor states
→ score & quality gate
→ explanation
→ persist snapshot
→ preview/publish
```

正式日终分析计划为 Asia/Shanghai 18:10，并在执行前检查 A 股交易日。

Prefect 技术状态与 WideGold 业务 AnalysisStatus 分离：Prefect 负责执行状态，`ops.analysis_runs` 负责业务生命周期。

## 6. LangGraph Agent Workflow

生产中保留四类 Graph：

- Event Intelligence：新闻/公告 → Structured Event；
- Factor Research：证据收集与 Candidate；
- Explanation：只基于 Fact Pack 解释已经计算出的结果；
- Scenario：用户假设 → Factor Shock → 模拟结果。

Graph 可以调用 LLM Router，但不能直接改生产权重、Publish Score 或绕过 Quality Gate。

## 7. LLM 路由

业务只引用 alias，不直接写模型字符串。设计层级：

```text
L1 Qwen        高频、低成本结构化任务
L2 DeepSeek    日常推理/映射/解释
L3 GPT兼容层   专家升级与复杂仲裁（可选）
```

当前代码支持 Provider Adapter + Runtime Config 路由。生产中 LLM 输出必须经过结构化 Schema/Validator；fallback exhausted 时事件子任务可以失败隔离，而不是让整个分析直接崩溃。

## 8. 数据与存储

业务 PostgreSQL 采用逻辑 Schema：

```text
iam
reference
raw
market
intel
decision
research
ops
scenario
```

关键原则：

- `release_ts <= data_cutoff_ts` 才能进入历史 Replay；
- Published Snapshot 不覆盖历史；
- 每次 Run 冻结 VersionSnapshot；
- Git YAML 是 bootstrap，DB ACTIVE 是生产真相；
- Redis 只保存可恢复状态，不是业务事实库。

## 9. External Bridge

为了隔离公网免费源的不稳定性，5 个特殊指标统一走 `external-bridge`：

```text
WideGold
   ↓ widegold.external-indicator.v1
External Bridge
   ├─ DR007 fixing proxy
   ├─ Index earnings revision
   ├─ Foreign activity
   ├─ Central bank gold
   └─ Gold supply/demand
```

Bridge 做重试、缓存、负缓存、语义转换和 PIT timestamp；WideGold 核心在入库前再次检查 `release_ts > as_of`，形成双层防未来数据保护。

## 10. 部署方案

V1 采用“模块化单体 + 独立运行时组件”，而不是微服务泛滥。

Docker Compose 负责 PostgreSQL、Redis、API、Web、Nginx、Prefect、External Bridge 和初始化任务。这样既保留清晰边界，又避免 Kafka/Kubernetes/Celery 等超出当前规模的复杂度。

## 11. 设计红线

- LLM 不直接给最终 Asset Score；
- 数据缺失不默认等于中性；
- Last-Known-Good 必须标记 stale；
- Manual Run 永远先 Preview；
- Quality Gate Fail 不覆盖 Published；
- 回测必须 Point-in-Time；
- Production Config 必须版本化并审计；
- API Key 不进入 Git/前端/日志；
- 免费源不能用错误 proxy 追求“全绿”。
