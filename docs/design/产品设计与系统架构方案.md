# 宽基与黄金市场环境智能研判系统 Agent

`面向普通投资者的宽基与黄金市场环境智能研判系统`

## 产品设计与系统架构方案

> 项目定位：只覆盖宽基指数与黄金，面向非专业投资者，强调“当前环境更利好谁、为什么、判断有多可信”，而不是直接预测短期涨跌或输出黑盒式买卖结论。  
> 技术目标：支持 Windows 10、Linux、Docker / Docker Compose 部署；支持 Qwen、Kimi、第三方 OpenAI-Compatible 模型接入。

---

# 第一部分：产品设计与系统架构结论

## 1. 产品定位

项目建议暂定名为：

**WideGold Agent / 宽基黄金智能研判 Agent**

一句话定位：

> 聚合宏观、政策、资金、市场、新闻与黄金相关信息，根据经过研究建立的“资产影响准则”，每日自动评估不同宽基指数及黄金的相对配置环境，并通过简单易懂的 Dashboard 向普通投资者展示。

项目不以“预测明天涨跌”为核心，而围绕三个问题展开：

1. 当前市场环境更利好哪类资产；
2. 为什么得出这个判断；
3. 当前判断的可信度和主要风险是什么。

目标用户为“韭菜级别”的普通投资者，因此产品输出必须做到：

- 少术语；
- 强解释；
- 强对比；
- 强证据；
- 强风险提示；
- 不直接输出不透明的“买/卖”结论。

## 3. 产品核心原则

项目核心不是“多个 Agent 辩论”，而是建立一套稳定的：

**因子准则库 + 每日事件影响分析 + 资产评分体系 + 风险与信心校验**

核心原则：

> LLM 负责找信息、读信息、理解信息、结构化信息和解释信息；  
> 规则引擎与量化评分模块负责最终判断。

即：

```text
数据
 ↓
事件
 ↓
因子
 ↓
影响准则
 ↓
资产评分
 ↓
风险 / 信心校验
 ↓
小白化解释
 ↓
Dashboard
```

这一原则应作为整个项目的架构红线。

- ETF资金；
- 外资；
- 融资余额；
- 财政政策；
- 地产政策；
- 资本市场政策；

### 4.2 Asset-Factor Matrix：资产—因子影响矩阵

不同资产对同一个因素的敏感度不同，因此不能共用一套统一权重。

建议构建：

```text
                         沪深300  A500  中证500  中证1000  创业板  黄金

国内流动性                  +2     +2      +3       +3       +3    0
经济复苏                    +3     +3      +3       +2       +2   -1
风险偏好上升                +2     +2      +3       +4       +4   -2
美债实际利率上升            -1     -1      -1       -1       -2   -4
美元走强                    -1     -1      -1       -1       -2   -3
地缘风险                    -1     -1      -2       -2       -2   +4
通胀预期上升                 0      0       0        0        0   +3
央行购金                     0      0       0        0        0   +3
```

矩阵中的权重不应完全由 LLM 临时生成，而应来源于：

- 深度研究；
- 历史验证；
- 专业研究资料；
- 经验规则；
- 后续复盘修正。

## 6. 每日资讯与事件分析 Workflow

不采用：

```text
新闻 → GPT → 推荐
```

采用：

```text
每日数据 / 新闻 / 政策
          ↓
      Collector
          ↓
清洗 / 去重 / 时间校验
          ↓
    Event Extractor
          ↓
 ┌────────┴────────┐
 ↓                 ↓
事件分类         强度判断
 ↓                 ↓
 └────────┬────────┘
          ↓
    Factor Mapper
          ↓
Factor Knowledge Base
          ↓
    Impact Engine
          ↓
   Asset Score Engine
          ↓
    Risk Reviewer
          ↓
     Daily Report
```

每日资讯最终需要被转换成结构化事件，例如：

```json
{
  "event": "Fed dovish",
  "factors": [
    "US_REAL_YIELD",
    "USD",
    "GLOBAL_LIQUIDITY"
  ],
  "direction": "positive",
  "strength": 4,
  "confidence": 0.91
}
```

随后再由规则层判断对不同资产的影响。

## 7. 影响评分模型

建议使用统一影响评分框架：

$
Impact =
Direction
\times Strength
\times Confidence
\times Relevance
\times Freshness
$

其中：

```text
Direction   = -1 / +1
Strength    = 1 ~ 5
Confidence  = 0 ~ 1
Relevance   = 0 ~ 1
Freshness   = 0 ~ 1
```

资产评分：

$
Score_{asset}
=
BaseScore
+
\sum w_i Impact_i
$

最终归一到 0～100。

建议用户侧映射：

| 分数 | 用户侧表达 |
|---:|---|
| 80–100 | 强势偏积极 |
| 65–79 | 偏积极 |
| 45–64 | 中性 / 观察 |
| 30–44 | 偏谨慎 |
| 0–29 | 强风险警示 |

除资产评分之外，还需要独立计算：

- Confidence Score；
- 数据完整度；
- 信息冲突程度；
- 新鲜度。

这样可以避免“评分很高但数据不足”的情况。

## 9. Agent 体系

不建议直接复制 TradingAgents 的：

```text
Bull ↔ Bear
Aggressive ↔ Conservative
多轮辩论
```

建议采用任务型 Agent：

```text
Macro Agent ───────────┐
Market Agent ──────────┤
Flow Agent ────────────┤
News / Event Agent ────┤
Gold Agent ────────────┤
                       ↓
                 Factor Engine
                       ↓
                 Score Engine
                       ↓
                 Risk Reviewer
                       ↓
                Report Generator
```

其中：

### LLM Agent 负责

- 新闻理解；
- 政策理解；
- 事件提取；
- 因子映射；
- 研究总结；
- 用户解释；
- 冲突识别；
- 报告生成。

### 确定性模块负责

- 因子权重；
- 评分；
- 影响计算；
- 数据新鲜度；
- Confidence；
- 风险校验；
- 历史记录。

## 10. 建议增加的增强 Workflow

### 10.1 Decision Review

每天记录：

- 当日资产评分；
- 当日主要原因；
- 后续 T+1 / T+5 / T+20 表现；
- 哪些因子判断正确；
- 哪些因子失效。

形成长期自动复盘体系。

---

### 10.2 Market Regime Detection

识别当前市场属于：

- 流动性驱动；
- 经济复苏；
- 风险厌恶；
- 成长行情；
- 小盘行情；
- 避险行情；
- 高波动环境。

不同市场状态下动态调整因子重要性。

---

### 10.3 Contradiction Checker

用于检测：

- 新闻与宏观数据冲突；
- 多个数据源结论冲突；
- 短期市场表现与基本环境冲突；
- LLM 分析之间冲突。

冲突越大，Confidence 越低。

---

### 10.4 Scenario Analysis

支持类似：

> 如果美联储突然降息会怎样？

系统根据已有 Factor Matrix 快速模拟：

- 沪深300；
- A500；
- 中证500；
- 中证1000；
- 创业板；
- 黄金。

属于非常适合普通投资者的交互型功能。

## 12. LLM 接入架构

模型能力不应写死在 Agent 中。

统一抽象：

```text
LLMProvider
    │
    ├── OpenAICompatibleProvider
    ├── QwenProvider
    ├── KimiProvider
    └── LocalProvider
```

第三方 OpenAI-Compatible 模型通过配置接入。

示例：

```env
LLM_PROVIDER=openai_compatible

LLM_BASE_URL=https://ca.memofun.net/v1
LLM_API_KEY=${SECRET}
LLM_MODEL=gpt-5.6-sol

LLM_QUICK_EFFORT=low
LLM_ANALYSIS_EFFORT=medium
LLM_RESEARCH_EFFORT=high
```

API Key 原则：

- 不进入 Git；
- 不写入前端；
- 不写死在代码；
- 仅通过服务端环境变量或 Secret 管理。

模型路由建议：

| 工作 | 推荐推理档 |
|---|---|
| 新闻去重 | minimal |
| 新闻分类 | low |
| Event → Factor | low / medium |
| 每日综合分析 | medium |
| 风险冲突检查 | medium |
| 因子深度研究 | high |
| 特别复杂的研究 | xhigh |
| max | 默认不使用 |

## 17. 第一阶段最终闭环

第一阶段最重要的不是把所有 Agent 做完，而是打通：

```text
Factor Knowledge Base
        ↓
Daily Event
        ↓
Factor Impact
        ↓
Asset Score
        ↓
Risk / Confidence
        ↓
Dashboard
```

形成最小完整闭环：

> “有依据地研究 → 有规则地判断 → 有证据地解释 → 有历史地复盘”。

# 第三部分：方案选择原因

## 1. 为什么不直接复制 TradingAgents

TradingAgents 最有价值的部分包括：

- Agent 状态管理；
- LangGraph；
- Checkpoint；
- 多角色 Workflow；
- Memory；
- Reflection；
- 模型 Provider 抽象。

但其中：

- Bull / Bear；
- Aggressive / Conservative；
- 多轮角色辩论；

更适合研究个股和模拟投资委员会。

本项目只有：

**宽基 + 黄金**

核心问题是：

> 宏观环境和市场环境对不同资产风格产生什么影响。

因此比起“不同 Agent 互相辩论”，更适合：

> 因子识别 → 影响分析 → 权重计算 → 风险检查。

这样可以减少：

- Token 消耗；
- LLM 随机性；
- 多轮幻觉传播；
- 同一数据不同时间得出完全不同结论；
- 难以回测的问题。

因此保留 TradingAgents 的工程思想，而不复制其决策结构。

---

## 2. 为什么借鉴 OpenFR

OpenFR 与本项目更匹配的部分主要是：

- 国内金融数据接入；
- AKShare；
- 轻量数据工具；
- Python 金融分析生态；
- Agent / Workflow 分离；
- 国内数据源适配。

宽基研究大量依赖：

- A股指数；
- ETF；
- 国内宏观；
- 市场成交；
- 资金；
- 利率；
- 政策。

因此 OpenFR 更适合作为：

**Data / Tool Layer 的参考。**

而 TradingAgents 更适合作为：

**Workflow / Memory / State Layer 的参考。**

---

## 3. 为什么“因子准则库”必须是项目核心

如果采用：

```text
每天新闻
 ↓
LLM 阅读
 ↓
LLM 判断
 ↓
推荐
```

会面临一个根本问题：

> 无法保证今天和明天使用同一套投资逻辑。

例如同一条：

> 美联储降息预期升温

LLM 今天可能认为：

- 黄金强利多；
- 创业板利多。

换一个 Prompt 或模型后又可能认为：

- 黄金已经 Price-in；
- 创业板影响有限。

因此需要把投资逻辑从 Prompt 中剥离，形成：

**Factor Knowledge Base。**

这样可以做到：

- 可解释；
- 可验证；
- 可修改；
- 可版本化；
- 可回测；
- 可复盘。

它实际上就是项目的“投资大脑”。

---

## 4. 为什么 LLM 不应该直接决定最终评分

LLM 非常适合：

- 文本理解；
- 新闻分类；
- 政策解读；
- 事件抽取；
- 研究总结；
- 关系发现；
- 用户解释。

但不适合作为唯一的数值决策模块。

直接让模型：

> 给沪深300打一个 0～100 分。

这种评分：

- 难复现；
- 难回测；
- 难解释分数变化；
- 难确定具体原因；
- 不同模型差异大。

因此采用：

> LLM 负责结构化事实，Rule / Quant Core 负责算分。

这能够在保留 LLM 理解能力的同时，提高系统稳定性。

---

## 5. 为什么使用“资产评分 + Confidence”

只有资产评分是不够的。

例如：

```text
黄金：82分
```

用户不知道：

- 数据是否完整；
- 新闻是否可靠；
- 多个来源是否冲突；
- 这个评分是不是只依赖一条新闻。

因此需要把：

**方向判断**

和：

**判断可信程度**

分开。

用户最终看到：

```text
黄金

当前评分：82
方向：强势偏积极
Confidence：86%
数据完整度：94%
```

比简单的“推荐黄金”更加可靠。

---

## 6. 为什么产品 UI 要像天气预报

目标用户不是专业投资者。

如果一打开就是：

- PE Band；
- Bollinger Band；
- RSI；
- Term Spread；
- Credit Spread；
- ERP；
- M1-M2；
- ETF Flow Z-score；

用户很难直接判断应该关注什么。

因此设计目标应该是：

> 后台复杂，前台简单。

后台可以非常专业：

```text
几十个因子
几十个数据源
Agent
规则引擎
评分模型
回测
```

但用户看到的是：

```text
今天更利好：
A500、沪深300、黄金

为什么：
1. 流动性改善
2. 美债实际利率下降
3. 风险偏好回暖

最大风险：
经济数据仍偏弱
```

这更符合面向普通投资者的产品定位。

---

## 7. 为什么初期资产数量要控制

宽基看似简单，但每新增一个资产就需要新增：

- 因子权重；
- 历史验证；
- 数据源；
- 基准；
- 事件敏感度；
- 风险逻辑；
- UI 信息；
- 历史评分。

如果一开始覆盖几十个指数，会造成：

> 看似全面，实际上每一个都做得不深。

先做：

- 沪深300；
- A500；
- 中证500；
- 中证1000；
- 创业板；
- 黄金。

已经能够覆盖：

- 大盘；
- 中盘；
- 小盘；
- 成长；
- 避险。

非常适合作为 MVP。

---

## 8. 为什么第一阶段采用 PostgreSQL，而不是复杂数据库组合

项目第一阶段的数据主要是：

- 时间序列；
- 事件；
- 因子；
- 资产评分；
- 新闻；
- 报告；
- Agent 状态；
- 研究资料。

PostgreSQL 已经可以覆盖大部分需求。

如果需要向量检索，再增加：

**pgvector**

即可。

相比：

```text
PostgreSQL
+
MongoDB
+
ElasticSearch
+
Milvus
+
Redis
```

第一阶段明显更简单。

原则是：

> 能用一个数据库解决的问题，不要先拆成五个数据库。

---

## 9. 为什么需要 Redis，但不需要一开始就使用 Celery

Redis 第一阶段可以用于：

- 缓存；
- Session；
- 临时结果；
- API 限流；
- Job 状态。

但任务数量初期不会非常巨大，因此：

**APScheduler + Worker**

足够。

等到后续出现：

- 大规模并发；
- 多任务；
- 重任务队列；
- 多 Worker；
- 自动重试；
- 分布式执行；

再切换：

**Celery + Redis**

即可。

这样避免过早工程化。

---

## 10. 为什么使用 FastAPI

主要原因：

- 与 Python 数据分析生态天然兼容；
- 与 Agent 框架兼容；
- 与 Pandas / NumPy / AKShare 兼容；
- 异步接口支持好；
- API 开发速度快；
- Docker 部署简单；
- Swagger 自动生成；
- 后续方便拆成服务。

因此适合作为整个项目后端入口。

---

## 11. 为什么推荐 LangGraph

项目存在大量长流程：

```text
新闻
 ↓
事件
 ↓
因子
 ↓
风险检查
 ↓
评分
 ↓
解释
 ↓
复盘
```

未来还会出现：

```text
研究
 ↓
证据
 ↓
规则生成
 ↓
人工确认
 ↓
版本更新
```

相比完全手写 Workflow，LangGraph 在：

- 状态；
- 节点；
- 重试；
- 条件跳转；
- Checkpoint；
- Debug；
- Agent 流程可视化；

方面更适合。

同时能够直接借鉴 TradingAgents 中的成熟工程思想。

---

## 12. 为什么要抽象 LLM Provider

用户当前可能使用：

- Qwen；
- Kimi；
- GPT；
- 第三方 OpenAI-Compatible API。

以后 API、价格和模型能力必然变化。

如果代码中直接出现：

```python
OpenAI(...)
```

将模型和业务逻辑耦合，后续切换成本会很高。

因此需要：

```text
业务
 ↓
LLM Router
 ↓
Provider
 ↓
GPT / Qwen / Kimi / Local
```

做到模型可替换。

---

## 13. 为什么不同任务使用不同推理档

项目每天会执行大量任务。

如果所有任务都使用：

```text
high / xhigh / max
```

会导致：

- 延迟变高；
- Token 成本提高；
- 日常任务没有必要。

例如：

新闻去重本质上不需要复杂推理。

而：

> “重新研究黄金核心驱动因素及其历史关系”

才需要高推理。

因此采用：

```text
简单任务 → minimal / low
普通分析 → medium
研究任务 → high
复杂研究 → xhigh
```

可以明显降低成本。

---

## 14. 为什么需要 Decision Review

任何投资分析系统都会犯错。

关键不是：

> 每天保证判断都正确。

而应该做到：

> 知道自己为什么错，并能持续修正。

因此每天保存：

```text
当时判断
+
当时证据
+
因子评分
+
最终资产评分
+
后续市场表现
```

后续就能分析：

- 哪些因子有效；
- 哪些因子经常失效；
- 哪些新闻被高估；
- 哪些状态判断错误；
- 哪个 Agent 经常出错。

最终形成：

```text
判断
 ↓
市场反馈
 ↓
复盘
 ↓
修正规则
 ↓
下一次判断
```

这是本项目长期演进的重要能力。

---

## 15. 为什么需要 Market Regime

同一个因子在不同市场环境中的影响可能不同。

例如：

> 流动性改善

在风险偏好很高的环境：

中证1000可能最受益。

而在经济衰退、风险厌恶阶段：

资金可能首先流向：

- 大盘；
- 高股息；
- 黄金。

因此未来不能永远使用固定权重。

Market Regime 是从：

**固定评分系统**

升级到：

**动态市场理解系统**

的重要一步。

---

## 16. 为什么需要 Docker Compose

项目包含：

- Web；
- API；
- Worker；
- PostgreSQL；
- Redis。

如果要求用户在 Windows 手动安装：

```text
Python
Node
PostgreSQL
Redis
各种依赖
```

部署成本会非常高。

因此采用：

```bash

```

是更合理的最终交付方式。

同时满足：

- Windows 10；
- Linux；
- 云服务器；
- NAS；
- 本地服务器。

# 结论

本项目不应定位成“AI 自动炒股系统”，而应定位成：

> **面向普通投资者的宽基与黄金市场环境智能研判系统。**

真正的核心竞争力不是：

- 使用了多少 Agent；
- 使用了多大的模型；
- Dashboard 多漂亮。

而是能否建立并持续优化：

```text
资产
 ↓
核心因子
 ↓
影响机制
 ↓
实时事件
 ↓
影响计算
 ↓
风险与信心
 ↓
历史验证
 ↓
持续复盘
```

因此第一阶段开发优先级建议固定为：

```text
1. Factor Knowledge Base
2. Asset-Factor Matrix
3. Data Collector
4. Event / Factor Mapping
5. Impact Engine
6. Score / Confidence Engine
7. Daily Workflow
8. Dashboard
9. Decision Review
```

第一阶段最值得优先产出的核心文件不是前端页面，而是：

> **《宽基 + 黄金因子体系与影响准则 V1》**

它将成为整个项目后续 Agent、事件分析、评分、Dashboard、复盘与回测的共同基础。
